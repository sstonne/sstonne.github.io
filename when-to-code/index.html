When to Code, When to Learn

Real-to-Sim-Verified Hybrid Code–Policy Skill Generation for Long-Horizon Robot Manipulation

Under review at IEEE Robotics and Automation Letters (RA-L)

Sumin Lee1 Jiwoo Kim1 Joo Yong Sim1,†

1Autonomous Mechanical Systems Lab, Sookmyung Women's University  ·  †Corresponding author

Paper (soon) Results BibTeX Homepage

LLM agents split a robot task into segments and decide, for each one, whether to write it as code or learn it with RL. The whole program is verified in a simulator aligned to the real scene before any policy is trained.

Abstract

Multi-stage robot manipulation requires both executable task composition and adaptive control of contact-rich interactions. Large language models can generate robot programs from language, but their code can be brittle during physical interaction. Reinforcement learning provides adaptive control but is inefficient when applied to an entire multi-stage task. We propose a real-to-sim-verified framework that converts a scene and a language instruction into a hybrid code–policy program. Segments that can be specified from scene geometry and executed with deterministic robot-API calls are assigned to code, whereas segments sensitive to contact dynamics or execution uncertainty are assigned to learned policies. Within a scene-aligned simulator, the Teleport Synthesizer uses simulator teleportation to bridge unresolved policy segments. This enables hybrid-program evaluation before policy training while extracting the handoff states and target states used to construct local observation and reward specifications. In our experiments, LLM-based code-only program generation without a reusable code skill achieved 0% and 8% program-generation success on table-leg assembly and T-block push-to-align, respectively, whereas learned hybrid programs achieved 93.7% and 84.2% end-to-end execution success in separate evaluations.

Problem & Why

Code is reliable until contact.
Learning is robust but expensive.

Research questionIn a multi-stage manipulation task, which steps should a robot write as code, and which should it learn?

Large language models can turn a sentence like "assemble the table legs into the tabletop" into robot code. That code works well for steps that geometry fully describes, such as grasping or moving above a hole. It breaks at steps that depend on precise contact, like a tight insertion, where a few millimeters of error decide success.

Reinforcement learning handles contact well, but learning a whole multi-stage task is slow and needs a task-specific observation and reward design every time. Neither tool alone fits a task that mixes both kinds of step.

Code only

Fast and interpretable, but brittle at contact. Code-only generation never completed table-leg assembly.

Learning only

Adapts to contact, but training the full task is inefficient and needs hand-designed rewards per task.

Hybrid, per segment

Keep the geometric steps as code and learn only the contact-critical ones, inside one executable program.

Methods & Findings

How the framework builds a hybrid program

  1. Align the real scene in simulation

    Four calibrated RGB-D cameras observe the workspace. Each object is segmented (SAM 2), turned into a 3-D mesh (SAM 3D), rescaled to its measured size, and posed in the robot base frame (FoundationPose). The result is a simulator that matches the real scene object by object, within 1.30 mm on average.

  2. Plan the task as [CODE] and [RL] segments

    A target-scene generator turns the command into a goal state. The LLM planner splits the task into ordered segments and labels each one: code if the robot API can do it and it tolerates pose error, RL if it is sensitive to contact or uncertain dynamics. The code generator writes Python robot-API calls and leaves a named placeholder for every RL call.

  3. Verify and repair the program before training anything

    Policies don't exist yet, so a Teleport Synthesizer stands in for each RL call: it teleports the objects to that segment's target state so the rest of the program can run. The verifier checks for runtime errors, collisions and goal satisfaction. When a rollout fails, an analyzer reads the logs and the code is revised; if a code step keeps failing at contact, the planner reassigns just that step from [CODE] to [RL].

    The same rollout records each RL segment's start state Spre and goal Spost, which become its local learning problem.

  4. Learn only the RL segments, then plug them back in

    An RL-Designer builds the observation space and generates reward code (Eureka-style), trains each segment with PPO in Isaac Lab, and revises the design from training feedback. The trained policy replaces the teleport proxy at the same call site. Verified code is saved as a reusable skill, and policy checkpoints can be reused by other programs for the same task.

1. Verify-and-repair makes code generation far more reliable

Compared with single-pass generation in the style of Code as Policies, iterative verification and repair reaches 100% on stacking and uprighting. A reusable code skill lifts the harder tasks further. Table-leg assembly still fails with code alone: four tight insertions give four chances to fail.

2. Learning only the contact step completes the tasks code could not

Segment policies succeed 96.6–98.3% of the time on their own step. Plugged into full programs, they bring peg-in-hole, table-leg assembly and T-block push to 84–95% end-to-end success, and transfer to other program versions of the same task with almost no loss.
